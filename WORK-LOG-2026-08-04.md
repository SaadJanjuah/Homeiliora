### 3. Mobile menu — fixed (the significant bug of the day)
- [x] **Symptom:** the hamburger opened to a ~68px sliver at the top of the screen. Only the first link was partly visible; the rest were unreachable.
- [x] **Cause:** `.site-header` carried `backdrop-filter`, and an element with `backdrop-filter` becomes the *containing block for any `position: fixed` descendant*. WordPress's mobile menu is a fixed full-screen overlay rendered inside the header, so it was sized and clipped to the header's own box instead of the viewport.
- [x] **Fix:** removed the filter rather than working around it — it never rendered anyway, because the header's `has-base-background-color` class paints an `!important` opaque background straight over the frosted effect.
- [x] Fixing that exposed three more faults in the overlay, none of which had ever been visible because the overlay had never opened to full size:
      - every label sat flush against the right edge (core positions overlay items from `--navigation-layout-*` variables, which the nav sets to `flex-end` for the right-aligned desktop bar — and they must be restated on the `<ul>` itself, since WordPress stamps a generated layout class onto it that re-sets them)
      - the overlay was white with black text **in dark mode too** (core hard-codes `#fff`/`#000` when the nav declares no colours of its own, at a specificity no plain class beats)
      - the submenu still rendered as a floating desktop dropdown card; it is a plain indented list now
- [x] Verified at 390×800 and 360×640 in **both** themes: overlay fills the viewport, all 9 links reachable and left-aligned with real padding, themed colours, close button reachable, no horizontal overflow
- [x] Desktop unaffected — header stays one row from 360–1000px; sticky header and theme toggle re-checked

> Worth recording: the first test run of this fix reported **OK** while three faults were still present. The assertions were too lax — flush-against-the-edge was not counted as clipped, and the background colour was not checked at all. Tightened, they caught all three. A passing check is only as good as what it actually asserts.

## ⚠️ Risks worth acting on

1. **Database backups exist on this machine only.** `backups/*.sql` is gitignored on purpose — the dump contains the admin password hash and must not go in a public repo. That means GitHub holds the *code* but none of the *content*. If this machine fails, the 8 posts, pages, menus and plugin settings are gone. **Keep a copy of `backups/homeiliora-db-2026-08-04.sql` somewhere off this machine** (private cloud drive, external disk) — just not the public repo.

## 📝 Notes for next time
- `dev/start-local.ps1` sometimes reports failure on the first run after a reboot: it waits a fixed 6 seconds for MySQL, which is not always enough for InnoDB recovery, so the health check fires while PHP is still waiting on the database. The site is fine a moment later. Replacing the fixed wait with a real connection check would stop it crying wolf.
